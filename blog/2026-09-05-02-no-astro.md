## What changed

A one-line instruction from the user: no Astro in this project. Nothing in the tree changed at the point this entry was first written. The decision is recorded here so the next session does not pick up `astro.config.ts` and carry on.

Two replacements were put to the user: Vite plus a small TypeScript build script, recommended, or Next.js with static export. The user chose Vite. The design, the plan and the migration all happened in this session; the sections below follow that order.

## Why it matters

Two days ago Astro was the load-bearing choice: it won over the already-installed Hugo because Hugo meant Go templates, and it won over Next.js because content collections gave a schema-at-build guarantee for free ([React for every UI component, inside Astro](2026-09-03-05-react-for-ui.md)). Removing it is the second tool the user has taken out this week, after [OpenSpec](2026-09-05-01-openspec-removed.md). The direction is a smaller stack, not a different one.

The constraints that produced the original choice all survive: TypeScript throughout, React for every visible component, a static site on GitHub Pages, and one schedule component that renders institution-local times at build and viewer-local times after hydration. The feeds and the JSON export keep their paths. Only the layer that glues those together is changing.

## How it works

The inventory of what Astro does today, which is the scope of whatever replaces it:

| Responsibility | Where it lives now |
| --- | --- |
| Routing and static path generation | `src/pages/` (two list pages, one page per defense, 43 feeds, one JSON file) |
| Typed content collections | `src/content.config.ts`, consumed by `site-data.ts` and `feed-data.ts` |
| React server rendering and `client:load` islands | the `.astro` pages around `DefenseSchedule` and `DefensePage` |
| Client bundling and CSS | Vite under Astro |
| HTML document shell | `src/layouts/Document.astro` |
| Base path for a Pages project site | `import.meta.env.BASE_URL`, threaded through `withBase` |
| Dev server and type check | `astro dev`, `astro check` |
| The build test | `test/build/helpers.ts` shells out to `astro build` |

Six source files import from Astro. Everything else is already plain TypeScript and React. The validator never touched Astro: `src/lib/records.ts` reads records and universities with js-yaml on its own, and the Zod schemas are the source of truth for both. That is why the schema-at-build guarantee is not lost by leaving: the build script can parse with the same schemas the validator uses, which is what the collections were doing behind the scenes.

The suite passes at 156 tests across 23 files with Astro still in place, which is the bar the replacement has to clear.

## The design (approved 2026-09-05)

The user approved this design in chat and chose to keep it here rather than in a separate spec file, in keeping with the removal of OpenSpec's planning artifacts.

**Architecture.** Two layers replace Astro. A pure generation module renders every page, feed and the JSON export into an in-memory list of output files, given the data, the site URL, the base path and the names of the built assets. A thin orchestrator runs Vite for the browser assets, runs the generator, and writes the files to `dist`. Everything under `src/lib`, `src/components`, `src/schema` and `src/validate` stays as it is.

**Data loading.** The content collections go away. A loader in `src/site/data.ts` reads records, universities and disciplines with the same `records.ts` functions the validator already uses, parses them with the same Zod schemas, and fails the build on the first invalid file or dangling university reference.

**Document and islands.** `Document.astro` becomes a React `Document` component that renders the whole html element. The two hydrated components keep their behaviour through a small island helper: on the server it wraps the component in a marked container and emits its props as a JSON script tag; each client entry finds those containers and calls `hydrateRoot` with the same component and props. Shell and PageIntro stay static markup with no JavaScript. Pages keep trailing slashes and the same URLs.

**Build pipeline.** One command, `node scripts/build.ts`, calling Vite programmatically twice: a client build of the two island entries and the stylesheet with a manifest, then a server build of the generator (Node strips types natively but cannot strip JSX). The orchestrator imports the server bundle, runs it, and writes the outputs. The server bundle lands under the node_modules cache directory. Site URL and base path stay as the two environment variables the deploy workflow sets.

**Dev loop.** `npm run dev` builds once, serves `dist` with Vite's preview server at the configured base, and watches `src`, `records`, `universities` and the disciplines file, rebuilding on change. Refresh to see changes. An on-demand dev server is a contained later addition if this grates.

**Types and dependencies.** The tsconfig stops extending Astro's preset and declares the equivalent strict settings itself. `tsc --noEmit` replaces `astro check`. Astro, its React integration and its checker leave; Vite becomes a direct dev dependency. No React plugin: Vite reads the JSX settings from the tsconfig, which is how the tests compile TSX today.

**Tests.** The build test stops shelling out: it calls the generator in-process with a stub asset manifest and keeps every current assertion on feeds and the export, plus new ones on the HTML pages. One separate slow test runs the real build into a temporary directory and checks that every asset a page references exists on disk. All 156 existing tests must still pass.

**Cleanup.** Delete `src/pages`, `src/layouts`, `src/content.config.ts`, the two Astro-only lib files, `astro.config.ts` and the local `.astro` cache. Update the ignore file, the README, the validate workflow's path filter, and the notebook's stack lines.

## The migration

Nine tasks, each ending in a passing test and a commit, on a `replace-astro` branch that was fast-forwarded into `main` the same afternoon after the suite passed again on the merged tree. Astro is gone from the tree and from the lockfile. What replaced it:

```
src/site/
  data.ts        records, universities, disciplines → published Defense[]
                 (the validator's own loaders and Zod schemas)
  assets.ts      island entry registry + Vite manifest → base-prefixed hrefs
  islands.tsx    <Island>: component in a marked <div>, props as a JSON <script>
  client/        hydrate.tsx helper; schedule.tsx and defense.tsx entries
  document.tsx   the <html> document as a React component
  pages.tsx      homePage / archivePage / defensePage → HTML strings
  generate.ts    every page, 43 feeds and the export as an in-memory list
  build.ts       Vite client build → manifest → Vite server build of the
                 generator → run it → write dist/
scripts/build.ts   CLI; reads SITE_URL and SITE_BASE as the deploy workflow sets them
scripts/dev.ts     build, serve dist with Vite's preview server, rebuild on change
```

Deleted: `src/pages/`, `src/layouts/`, `src/content.config.ts`, the two lib files that wrapped `astro:content`, `astro.config.ts`, and the test helper that spawned `astro build`. The tsconfig no longer extends Astro's preset; it spells out the same strict options and `tsc --noEmit` is the type check. Three packages left, Vite became a direct devDependency (it was already there underneath Vitest).

Before and after, from the terminal:

| | Astro | Build script |
| --- | --- | --- |
| Tests | 156 in 23 files | 178 in 28 files |
| Build test | spawns `astro build`; the long pole of a 9.4 s suite | in-process generator, 0.5 s; one separate real-build test, 0.7 s; suite 6.3 s |
| `npm run build` | not timed | 68 files in 253 ms (fresh clone) to 1.2 s |
| Client JS, all chunks | ~203 KB in five files | ~201 KB in three files |
| `node_modules` top-level entries | ~280 | 83 |
| Lockfile | 6,890 lines | 2,121 lines |

The output is the same set of 68 files at the same paths, and the fresh-clone check (clone, `npm ci`, type check, tests, build) passed on the first run.

## How it works

The build is two Vite calls and a loop. The first bundles the two client entries and the stylesheet with a manifest, which yields the hashed asset names the document needs. The second is a *server* build of the generator, needed for one reason: Node 24 strips TypeScript types natively but cannot strip JSX, and the generator imports the page components. The orchestrator imports that bundle and calls `generate()`, which loads the data, renders each page with `renderToString`, builds the calendars and the export, and returns them as a list. Writing the list to disk is the last step.

The island pattern is what keeps the "same component, two states" design from the [React decision](2026-09-03-05-react-for-ui.md). On the server, `<Island>` renders the component inside `<div data-island="DefenseSchedule">` and emits its props as `<script type="application/json">` right after it, with `<` escaped so a closing script tag inside a thesis title cannot break out. In the browser, the entry finds each container, parses the JSON next to it and calls `hydrateRoot`. The static markup remains the no-script fallback, the hydration test from the component suite still asserts zero mismatch warnings, and the test for the helper hydrates two islands from one document.

The data layer lost nothing by leaving content collections: they had been calling js-yaml and the Zod schemas behind the scenes, and the validator already had its own copy of that logic in `src/lib/records.ts`. The site now imports the same functions, so the build and the validator agree by construction rather than by matching a framework's parser.

## Surprises

- **React 19 does not emit a doctype** when the root is `<html>`. The document renderer prepends it; a test asserts exactly one.
- **The build test went from the long pole of the suite to half a second** by testing the generator instead of the artefact. The old test needed a child process, a scratch directory and an environment scrubbed of the variables Vitest leaks; the new one calls a function with a stub manifest and a pinned clock, which also stops the feed-window assertions from drifting as the seed defenses age.
- **The server bundle has to live inside the project.** Vite externalises `react-dom`, `react/jsx-runtime` and `js-yaml` from the server build, so a bundle written to a temp directory cannot resolve them. It lives under `node_modules/.phdtv/`, and the dev loop imports it with a cache-busting query because Node's module cache would otherwise serve the first build's code forever.
- **Vitest's `NODE_ENV=test` reaches child processes.** Left in place it makes Vite bundle React's development build. The bundle test strips it, along with the `import.meta.env` mirrors that bit the Astro-era helper.
- **The dev script printed no address at first.** It asked Vite's preview server to print its URLs, but it also ran Vite at the `warn` log level, which silences that output. The user noticed within the hour; the script now prints `Serving … at http://localhost:4321/phdtv/` itself.
- **The Astro-specific gotchas evaporated** with the framework: the `~7.2.10` pin, the `BASE_URL` leak. They are archived under `.devlog/archive/astro.md` in case the history is ever needed.
- **A `.astro/` directory reappeared** after being deleted, with fresh content types inside. Nothing in the repository writes it any more; an editor extension for Astro does when it notices the project. It is no longer ignored by git, so it shows up as untracked until that extension is disabled for this workspace.
